# 下一完整单元：从 LT 迁移到 ET

状态：本单元现已实施并通过 LT/ET 对照验收；具体错误修复、测试命令、真实 EAGAIN 证据及覆盖边界见 [spec.md](spec.md) 末尾的 ET 子单元验收记录。下文保留实施前的设计和验收计划。前置学习总结见 [stage_1.md](stage_1.md)。

## 1. 目标与边界

完成单线程非阻塞 ET 的监听、接收、发送策略，并与 LT 基线对照验证。

本单元不加入 Keep-Alive、流水线、线程池、数据库、定时器、EPOLLONESHOT，不修改 HTTP 路由和正文长度规则。不预设 ET 更快，也不以 QPS 作为验收标准。

完成后仍是一请求一响应、Connection: close；Connection 保留 Buffer、解析器、output、sent、responding。文件读取和响应构造仍同步执行。

## 2. 为什么不能只加 EPOLLET

当前 LT 版本每次事件只调用一次 recv/send。只要条件持续满足，后续 epoll_wait 仍可返回对应事件。

ET 不保证对一个一直保持就绪、尚未被处理完的 socket 反复通知。例如请求已有 12 KiB 在内核接收缓冲区，而一次 recv 只读 4096 字节：

```text
收到可读事件 → 读 4 KiB → 解析 NeedMore → 返回 epoll_wait
剩余数据还在内核，客户端又不再发送 → 不能指望一定有下一次通知
```

发送同理：一次正返回值可能只是部分发送，socket 仍可写；若立即返回等待下一次边沿，响应可能停住。

可靠的基本策略是：非阻塞 I/O 持续尝试，直到 EAGAIN，或当前应用任务已结束，或连接必须关闭。

“边沿”是理解通知语义的模型，不要机械理解为“每次 send 对应一次事件”或“永远只通知一次”。

## 4. 实施方案：一个功能单元，三个工作块

### 工作块 A：保留可切换的 LT 基线

建议给 Server 增加一个最小构造参数 `bool useET = false`，保存为成员。默认仍是 LT；main 中显式选择 ET。它只用于学习和对照测试，不扩展命令行配置系统。

统一生成触发标志：LT 为 0，ET 为 EPOLLET。将它用于三处注册：

| 位置 | 事件 |
| --- | --- |
| Init 注册监听 socket | EPOLLIN 加触发标志 |
| AcceptClients 注册客户端 | EPOLLIN、EPOLLRDHUP 加触发标志 |
| 请求完成后 MOD 到发送阶段 | EPOLLOUT 加触发标志 |

MOD 会替换事件掩码，不是追加。如果只在 ADD 时添加 EPOLLET，随后 MOD 漏掉它，客户端会在发送阶段退回 LT。

Epoller 保持通用封装，不在内部偷偷对所有事件追加 EPOLLET。事件策略属于 Server。

### 工作块 B：接收循环与应用状态转换

AcceptClients 已循环到 EAGAIN，保持现有逻辑，不另行重写。

HandlerClientEvent 的接收部分改成循环。每次成功接收后立即 Append 并 Parse，而不是先无限收集数据，最后才检查大小。

```text
尝试 recv
├─ n > 0
│  → Append → Parse
│     ├─ NeedMore：继续 recv
│     └─ Complete / 错误：构造响应、切换 EPOLLOUT，停止接收本次请求
├─ n == 0：请求尚未完整则关闭，立即结束当前连接处理
├─ EINTR：重试 recv
├─ EAGAIN/EWOULDBLOCK：保留状态，结束本轮接收，等待后续数据
└─ 其他错误：关闭，立即结束当前连接处理
```

两个不同的“完成”必须区分：

- EAGAIN：现在内核没有更多可读数据，不代表 HTTP 请求已经完整。
- Complete：当前 HTTP 请求完整，不需要为了追求 EAGAIN 再读下一个请求。当前不支持连接复用，切换响应阶段是合法停止点。

特别注意：完整请求伴随 FIN 时，Parse 成功后应进入发送阶段，不要继续读到 0 又把应发的响应丢掉。错误请求也应尽快构造错误响应，不等待客户端发完超限正文。

本轮可继续在 MOD 到 EPOLLOUT 后等待通知。Linux MOD 会重新检查当前就绪状态，不要求对端再做一个动作；无需同时引入“立即发送”优化。

### 工作块 C：发送循环与偏移维护

```text
只要 sent < output.size()
  → send(output + sent, size - sent)
     ├─ n > 0：sent += n，继续尝试发送
     ├─ EINTR：重试 send
     ├─ EAGAIN/EWOULDBLOCK：保留 output/sent，返回事件循环
     └─ n == 0 或其他错误：关闭，立即返回
发送完成 → 关闭连接，立即返回
```

没有数据待发时不订阅 EPOLLOUT。当前注册的写事件包含 EPOLLET；真实 EAGAIN 后保持写关注，等待可写条件再次出现即可，不需要 EPOLLONESHOT 重置。

相同的耗尽循环也能在 LT 下正确工作，因此优先共用读写逻辑，避免维护两份协议处理代码。LT/ET 主要通过事件标志切换。

关闭并删除连接后，Connection 引用立即失效。新增循环里的 break/return 需要逐处判断，不能机械替换：break 只结束最近的一层循环，return 才结束当前成员函数。

## 5. 与现有测试衔接时的一个重要问题

现有 send_probe 会人为返回 EAGAIN，而并不保证 socket 真的不可写。在 LT 下仍有持续可写通知，这种注入可以恢复；在 ET 下，如果没有真实的就绪变化，直接等待下一次事件可能停住。

因此，不能将旧探针原样用于 ET，再把停住直接判定为 ET 服务器错误。

本轮测试调整原则：

- 保留旧探针的 LT 注入验收能力。
- ET 使用探针的记录/缩小发送缓冲区模式，关闭人工 EAGAIN 注入。
- ET 发送循环应在慢客户端背压下自然遇到内核 EAGAIN，并记录实际证据。
- 如需 ET 故障注入，必须额外设计与就绪通知一致的恢复机制；不为迁就不真实的注入而改服务器事件策略。

这里既要验证“遇到 EAGAIN 后不丢状态”，也要验证“什么时候会重新有事件”。不能只检查 errno 数值。

## 6. 验收矩阵，由 agent 执行

### LT 回归

- 构建、现有 CTest 和完整 LT 网络脚本。
- 新的共用循环不能破坏已经验收的 LT 行为。

### ET 专项与共用网络回归

1. 六份现有 Python 脚本：请求格式、长度、分片及表单等行为一致。
2. 一次提交超过 4096 字节的请求，不依赖客户端补发数据即可处理完成。
3. 请求分批到达，第一次读到 EAGAIN 后，后续数据到达仍能继续解析。
4. A 只有半个请求时 B 完成；A 补齐后成功。
5. 完整请求（含 64 KiB echo）后 SHUT_WR 正常响应；不完整请求后 EOF 不返回成功。
6. 8 MiB 响应、客户端暂停读取：记录真实部分发送和内核 EAGAIN；恢复读取后正文逐字节一致，另一连接仍可响应。
7. 少量已排队连接均被 accept，不残留等待到下次新连接才处理的情况。不做高并发压测。
8. RST、发送中断连、发送完成及错误后 fd 恢复基线。
9. 资源生命周期测试分别覆盖 LT 和 ET；如增加构造参数，默认 LT 的既有调用应继续有效。

若仅网络结果成功但未观察到真实 EAGAIN，应明确记录未覆盖，不用“应该发生过”代替证据。必要时使用确定性 socketpair 小实验验证读/写耗尽语义，并和 HTTP 集成结果分开报告。
